# Roadmap — Sukshma-Jignaasa

All phases follow AI Spec-Driven Development principles: every feature is fully specified (mission, user stories, data contracts, AI prompt behaviour, guardrails, and acceptance criteria) before implementation begins.

---

## Phase 1 — The Diagnostic Companion (MVP)

**Goal:** Ship a working daily symptom companion with AI-powered pattern narration for the undiagnosed self-advocate.

**Success metric:** A patient can log symptoms for 30 days and receive a structured pattern summary they can bring to a specialist appointment.

### Features

| Status | Feature | Description |
|--------|---------|-------------|
| 📋 | Patient onboarding | Account creation, symptom profile setup (body systems, known conditions, current medications), privacy consent |
| 📋 | Quick-log widget | One-tap severity logging for saved symptoms; body system selector; duration picker |
| 📋 | AI daily check-in | Conversational AI check-in that extracts triggers, context (sleep, activity, food, stress), and new symptoms from free-text input |
| 📋 | Symptom timeline | Visual longitudinal timeline of all logged symptoms, filterable by symptom type and body system |
| 📋 | Pattern Narrator | AI surfaces temporal patterns, co-occurrences, and trigger correlations across the logged history. Weekly cadence. Plain-language output. |
| 📋 | Medblocks FHIR storage | All symptom logs stored as FHIR `Observation` resources via the Medblocks API |
| 📋 | Appointment prep summary | AI-generated pre-visit structured summary (top symptoms, timeline, correlations, suggested questions). Patient reviews before sharing. |
| 📋 | Safety guardrails | Hard refusal list, uncertainty framing on all AI outputs, human review gate before clinical sharing |
| 📋 | PWA packaging | Next.js app installable on iOS and Android home screen. Offline logging with background sync. |

### Out of Scope (Phase 1)

- Hypothesis Surfacer (requires ≥60 days of data for meaningful output — deferred to Phase 2)
- EHR connection and FHIR data pull
- Wearable/sensor integration
- Clinician-facing portal
- Post-diagnosis monitoring mode

## Phase 2 — The Intelligence Layer

**Goal:** Activate the Hypothesis Surfacer, add EHR connectivity via Medblocks, and build the clinician handoff capability.

**Success metric:** A patient with 60+ days of data receives a hypothesis profile they present to a specialist, who orders a targeted diagnostic workup based on it.

### Features

| Status | Feature | Description |
|--------|---------|-------------|
| 📋 | Hypothesis Surfacer | AI compares patient symptom fingerprint against rare disease knowledge base. Produces ranked hypothesis profiles with explicit uncertainty, plain-language explanations, and mandatory specialist-discussion CTA. Unlocks at 60 days. |
| 📋 | EHR connection (Medblocks OAuth) | Add the skill from medblocks/skills and understand the full patient access integration flow | Using this flow the patient connects their EHR account via Medblocks patient session. Historical FHIR records (labs, diagnoses, medications) are pulled and incorporated into the AI's analysis context. |
| 📋 | Rare disease knowledge base | Curated structured profiles of 50+ rare conditions most commonly in the EDS/POTS/MCAS/autoimmune overlap cluster. Used as retrieval context for the Hypothesis Surfacer. |
| 📋 | Shareable clinical report | Patient generates a formatted PDF/structured document of their symptom history and AI-identified patterns for direct handoff to a specialist. Includes a clear "generated by AI companion" disclosure. |
| 📋 | Push notifications | Daily check-in reminders, pattern milestone alerts ("new correlation detected in your last 30 days") |
| 📋 | Wearable integration (Phase 2b) | Apple Health / Google Fit data pull for heart rate, HRV, sleep stages. Incorporated as additional signal in pattern analysis. |

## Phase 3 — The Monitoring Companion

**Goal:** Build the post-diagnosis mode and enable longitudinal disease management for patients who receive a confirmed rare disease diagnosis.

**Success metric:** A diagnosed patient and their specialist share a structured disease activity log and care plan through the app.

### Features

| Status | Feature | Description |
|--------|---------|-------------|
| 📋 | Diagnosis confirmation flow | In-app workflow for patient to record a confirmed diagnosis. Transitions the app from diagnostic to monitoring mode. |
| 📋 | Disease-specific monitoring | Symptom tracking calibrated to the confirmed condition's known activity markers (e.g. autonomic scores for POTS, joint stability for hEDS, mast cell trigger tracking for MCAS) |
| 📋 | Care plan tracking | Medication logging, physiotherapy milestones, specialist appointment scheduling linked to care plan steps |
| 📋 | Disease progression summaries | Longitudinal activity summaries replacing the hypothesis surfacing output |
| 📋 | Clinician-facing portal (read-only) | Specialist can view a patient's shared symptom history, activity trends, and care plan adherence |
| 📋 | Research contribution (opt-in) | Patient can opt in to contributing de-identified data to a rare disease research registry |
| 📋 | Community features | Optional connection to patient communities organised by condition |

## AI Spec Milestones

Each AI mode requires a completed spec before implementation begins. Spec components per mode:

1. **Purpose statement** — what clinical problem this mode solves
2. **Input contract** — exactly what data the AI receives (data types, date ranges, field names)
3. **Output contract** — exact structure of the AI's response (JSON schema or typed interface)
4. **Prompt specification** — full prompt template with all guardrail language
5. **Guardrail list** — what the AI must never say or do in this mode
6. **Evaluation dataset** — minimum 10 synthetic patient scenarios with expected outputs
7. **Acceptance criteria** — observable, testable pass/fail conditions
